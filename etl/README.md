# ETL исходных ставок в Core

Пайплайн обрабатывает `loading_date` в интервале `[start_date, end_date)`. Текущие записи берутся из `public.prices`; актуальные валидные результаты записываются в `core.prices`, ошибки — в `dq.quarantine_prices`. Затем он полностью пересчитывает `mart.route_card` по всем имеющимся данным Core.

## Запуск в Docker

`docker compose up` поднимает PostgreSQL, pgAdmin и однократную цепочку Core → Mart → ML. После изменения кода используйте `--build`. По умолчанию ETL обрабатывает `[2023-01-01, 2028-01-01)` — весь диапазон текущего генератора. Границы можно задать в `.env` через `ETL_START_DATE` и `ETL_END_DATE`, дату среза — через `MART_AS_OF_DATE` (по умолчанию `2026-10-26`). Успешное завершение контейнера ETL с кодом `0` ожидаемо; затем запускается сервис `ml`.

Пересчёт отдельного периода без изменения настроек других сервисов:

```powershell
docker compose run --rm etl --start-date 2026-09-01 --end-date 2026-10-01
```

Эта команда пересчитывает указанный период Core и затем **всю** витрину Mart. Если нужно изменить дату среза, добавьте `--as-of-date 2026-09-30`; без аргумента используется `2026-10-26`.

Просмотр логов: `docker compose logs etl`. PostgreSQL не следует пересоздавать во время обработки.

## Локальный запуск Python

При настройках Docker по умолчанию в PowerShell:

```powershell
$env:PGHOST = '127.0.0.1'
$env:PGPORT = '5432'
$env:PGDATABASE = 'deals_bigdata'
$env:PGUSER = 'de_user'
$env:PGPASSWORD = 'local_de_password'
uv run python -m etl.pipeline --start-date 2026-09-01 --end-date 2026-10-01
```

Переменные подключения стандартные для libpq; `.env` автоматически читается Docker Compose, но не этим Python-скриптом. Приведённый пароль — только локальный пример.

## Как работает загрузка

1. Пайплайн берёт общую advisory-блокировку: два запуска одновременно запрещены.
2. В транзакции `REPEATABLE READ` собираются ID текущих исходных записей окна и ранее сохранённых записей Core/карантина этого окна. Поэтому можно обнаружить записи, которые были перенесены на другую дату или удалены из полного источника.
3. SQL проверяет существование городов через `EXISTS`, ищет точный курс и собирает все причины ошибок. Если на одну валюту и дату найдено несколько курсов, запись помещается в карантин: случайный курс не выбирается.
4. Для валидных строк заполняются только отсутствующие категории, цена приводится к RUB и округляется до двух десятичных знаков. Цена и курс источника имеют тип `double precision`: приведение к `numeric` не восстанавливает потерянную точность. Для RUB курс равен 1.
5. Старое состояние выбранных ID удаляется из Core и карантина; актуальные результаты пакетно вставляются в соответствующую таблицу. `detected_at` сохраняется при непрерывном нахождении записи в карантине; `last_run_id` обновляется на каждом запуске.
6. В той же транзакции полностью пересчитывается Mart. При ошибке любого шага откатываются и Core, и карантин, и витрина. Логи `core_prepared` и `mart_started` относятся к ещё не зафиксированной транзакции; успех подтверждает только `etl_succeeded`.

Синхронизация удалений предполагает полный источник `public.prices`. Изменения вне запущенного окна автоматически не обнаруживаются; для них нужен backfill затронутого окна либо отдельный механизм отслеживания изменений. Core сохраняет и `is_fact=false`, и составные маршруты, и отмеченные выбросы: фильтры рыночной витрины относятся к следующему этапу. Исходный `outlier_mark` не пересчитывается; записи последнего дня снимка 2026-10-26 ещё могут быть не размечены ночным процессом.

Логи запуска — JSON-строки. Количество срабатываний отдельных причин может превышать число строк карантина, так как у записи бывает несколько ошибок. Повторный запуск обновляет технические `last_run_id` и `refreshed_at`, но не должен менять бизнес-данные при неизменном источнике. На март влияет весь уже загруженный Core, не только окно текущего запуска.

## Пересчёт карточки маршрута

Витрина автоматически пересчитывается после Core через обычную команду ETL. При необходимости можно отдельно запустить полный пересчёт витрины из PowerShell:

```powershell
Get-Content -Raw -Encoding UTF8 sql/05_refresh_route_card.sql | docker compose exec -T postgres psql -U de_user -d deals_bigdata -v ON_ERROR_STOP=1
```

Дата среза по умолчанию — `2026-10-26`; другую дату можно передать в `psql`, добавив `-v as_of=2026-09-30` после `-v ON_ERROR_STOP=1`. Если учётные данные или база переопределены, в команде нужно указать соответствующие значения. SQL использует команды `psql` и рассчитан на запуск через него.

Отдельный пересчёт использует общую блокировку с ETL Core, согласованный снимок `REPEATABLE READ` и заменяет весь текущий Mart в одной транзакции; при ошибке предыдущая витрина остаётся доступной. При обычном запуске Core и Mart обновляются одной транзакцией. Расчётная часть SQL общая для обоих вариантов и встраивается из `sql/05_refresh_route_card.sql` между явно отмеченными маркерами. При повторном пересчёте бизнес-поля должны совпадать при неизменных данных и `as_of`; `refreshed_at` изменится.

Одна строка Mart — месяц × направление × группа кузова × весовая категория. `price_dates` группируется по цене и месяцу; для разных типов кузова одной стандартной группы цена учитывается один раз. При отсутствии связей `price_body_types` используется `core.prices.body_type`, затем `UNSPECIFIED`. Если ID типа существует в связи, но отсутствует в справочнике типов или не относится к четырём названным группам, он попадает в `OTHER`. Русские названия групп доступны через `JOIN mart.body_groups USING (body_group)`.

Для свежести используется максимальная допустимая `price_dates.price_date` внутри ячейки, а не дата загрузки или доказанная дата физического рейса. Эта интерпретация формулировки задания является проектным допущением. Источники пока не версионируются: `as_of` ограничивает даты развёртки, но не восстанавливает старые версии ставок или справочников. Квартильные расчёты `percentile_cont` в PostgreSQL выполняются с приведением к `double precision`, затем результат хранится в `numeric`.

Маленькие контрольные наборы и отдельные тестовые БД подготавливает общий runner. Вспомогательный `tests/route_card_fixture.sql` используется тестами извлечения ML и не предназначен для рабочей БД.

## Проверки

Запуск всех проверок через Docker Compose:

```bash
docker compose run --rm --build tests
```

Runner автоматически создаёт отдельные временные БД, подготавливает схемы и тестовые данные, запускает проверки и удаляет созданные БД. Рабочие таблицы не очищаются; вручную задавать переменные окружения для включения тестов не требуется.
