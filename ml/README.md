# ML-пайплайн: признаки, обучение, прогнозы и публикация

Пайплайн извлекает очищенные ставки, строит признаки и обучает
`CatBoostRegressor` с хронологической validation внутри train. Модель,
метрики и прогнозы сохраняются в файлы. Полный снимок прогнозов публикуется
в `mart.ml_price_predictions` одной транзакцией.

## Запуск

При обычном `docker compose up --build` сервис `ml` выполняется после успешного
ETL: подготовка признаков → обучение → файлы → публикация в PostgreSQL.
Каталог результатов примонтирован в `ml/artifacts` на хосте. Между этапами
передаются точные пути каталогов; выбор по имени «последнего» каталога не используется.
Общая дата среза Mart и ML задаётся `MART_AS_OF_DATE` в `.env`, потоки и seed —
`ML_THREAD_COUNT` и `ML_RANDOM_SEED`. Для повтора полной ML-цепочки на готовом Core:

```powershell
docker compose run --rm --no-deps ml
```

Чтобы повторить только подготовку признаков при уже заполненном Core:

```powershell
docker compose run --rm --no-deps ml-features
```

`ml-features` находится в необязательном профиле `features`; явный запуск сервиса
доступен без включения профиля и не запускает вторую подготовку при обычном `up`.

### Локально из PowerShell

Сначала поднимите PostgreSQL и загрузите Core существующим ETL. Для локального
запуска настройте стандартные переменные подключения (значения возьмите из `.env`;
Python не читает этот файл автоматически):

```powershell
uv sync --locked
$env:PGHOST = '127.0.0.1'
$env:PGPORT = '5432'
$env:PGDATABASE = 'deals_bigdata'
$env:PGUSER = 'de_user'
$env:PGPASSWORD = '<POSTGRES_PASSWORD из .env или docker-compose.yml>'
uv run python -m ml.prepare_dataset --as-of-date 2026-10-26 --output-dir ml/artifacts
```

## Контракт

- Зерно — одна строка на `core.prices.source_price_id`. `price_dates` не участвует.
- История: `is_fact`, `price_type IN (1,2,3,4,5,9)`, `NOT complex`,
  `NOT outlier_mark`, `price_rub > 0`, `distance > 0`.
- `train`: `[2026-07-26, 2026-10-05)`; `test`: `[2026-10-05, 2026-10-26]`.
  Для другой даты среза границы пересчитываются: минус 3 календарных месяца и
  минус 21 день. Обе исторические выборки должны быть непустыми.
- `future`: дата погрузки после среза, те же фильтры факта/типа/простого маршрута
  и расстояния, **без фильтра по цене или `outlier_mark`**. Цена маскируется в SQL
  и повторно в Python. Верхняя граница будущего не задаётся.
- Минимальный `cities.id` на `gc_id` определяет город, полное имя и координаты.
  Регион — весь текст после первой запятой с удалением крайних пробелов.
  Если запятой или региона нет, используется `UNKNOWN`. Синонимы не объединяются.
- `primary_body_group` описывает `core.prices.body_type`, а шесть флагов
  `allows_*` — допустимые группы из `price_body_types`. Только при отсутствии
  связей используется основной тип. Неизвестный заданный тип → `OTHER`,
  незаданный тип → `UNSPECIFIED`. Несколько типов одной группы дают один флаг.
- Веса и объёмы неотрицательны, расстояние положительно; все три конечны.
  Отсутствие города останавливает подготовку. Отсутствующие или недопустимые
  координаты заменяются на `NaN`, без вычисления среднего по выборкам.

## Признаки

28 признаков, их порядок и типы определены в `features.py`:

- 7 физических чисел: расстояние, вес, объём, четыре координаты;
- 5 строковых категорий: два региона, основной кузов, весовая и объёмная категории;
- 6 бинарных флагов допустимых кузовов;
- 10 календарных чисел: год, месяц, день недели (понедельник = 0), день года,
  а также sin/cos месяца, дня недели и дня года.

Для циклического кодирования используются `(month-1)/12`, `weekday/7`,
`(day_of_year-1)/365.25`. Например, для понедельника `weekday_sin=0`,
`weekday_cos=1`. Скейлеры, импутация по среднему, лаги, скользящие средние и
статистические фильтры выбросов не обучаются. Категории остаются строками для
будущего `CatBoostRegressor`.

Цены, валютные компоненты, `outlier_mark`, групповые агрегаты, ID ставок/городов,
названия городов, организация и абонент не входят в `X`. Признаки выбираются
явным списком: новая колонка извлечения не становится признаком автоматически.

## Результат и повторный запуск

Каждый запуск создаёт отдельный каталог `ml/artifacts/dataset-<UUID>/`:

```text
manifest.json
train/  X.parquet, y.parquet, metadata.parquet
test/   X.parquet, y.parquet, metadata.parquet
future/ X.parquet, y.parquet, metadata.parquet
```

В каждой выборке строка с одним номером в трёх файлах относится к одной ставке.
`metadata` содержит её ID, дату, коды и имена городов. `y` содержит только
`target_price_rub`; в `future` это всегда пропуски. Parquet сохраняет числовые
типы и пропуски, в отличие от неявного восстановления типов при чтении CSV.

`manifest.json` записывается последним: каталог без него считается незавершённым.
В нём сохранены границы, порядок/типы признаков, версии библиотек, хеши кода,
извлечения и файлов, числа строк, пропусков и неизвестных регионов, новые категории
относительно train и константные признаки. Подготовка не меняет БД. Повторный
запуск создаёт новый артефакт для сравнения; строки внутри набора не дублируются.
При одинаковом снимке и коде содержимое таблиц детерминировано, UUID и время
запуска различаются. Артефакты исключены из Git и Docker build context.

Чтение использует read-only `REPEATABLE READ` и совместимую с ETL advisory lock:
две подготовки могут читать одновременно, пересекающаяся запись Core/Mart
останавливает подготовку с ошибкой для последующего повтора. Это правило
действует для наших пайплайнов; произвольные изменения SQL не обязаны брать lock.
JSON-события пишутся в stderr терминала: начало, успех со статистикой или ошибка.

## Ограничения данных

`as_of` задаёт границы по дате погрузки; это **не** восстановление исторической
версии базы. Core и справочники содержат текущее состояние, а дата завершения
перевозки отсутствует. `is_fact` и дата погрузки служат приближением доступности
факта. Будущие кандидаты также уже прошли ценовые/валютные проверки Core: заявки
без цены в этой архитектуре не доходят до ML. Для настоящего production-скоринга
нужен отдельный источник плановых заявок без требований к известной цене.

На коротком окне одного 2026 года нельзя проверить годовую сезонность и
межгодовой тренд. Наличие гармонических признаков этого ограничения не снимает.
Метрики обучения рассчитываются только для истории. Они не измеряют качество
на будущих заявках без фактической цены и не гарантируют качество на реальных данных.

## Обучение CatBoost и сохранение прогнозов

Выберите завершённый каталог признаков с `manifest.json`. Путь задаётся явно:
пайплайн не выбирает случайный или последний каталог автоматически.

```powershell
uv sync --locked
uv run python -m ml.train_model --dataset-dir 'ml/artifacts/dataset-<UUID>' --output-dir ml/artifacts
```

Замените `<UUID>` на имя существующего набора. PostgreSQL для этого шага не нужен:
используются только ранее подготовленные файлы.

Порядок выполнения:

1. Проверить версию контракта, SHA-256 девяти входных Parquet-файлов, порядок
   признаков, число строк, уникальность ID и границы дат. Future-цены должны
   быть пропусками. Категории передаются в CatBoost строками через `cat_features`.
2. Внутри train выделить последние 14 дней под validation:
   `fit = [2026-07-26, 2026-09-21)`,
   `validation = [2026-09-21, 2026-10-05)`.
   Строки одной даты не разделяются между fit и validation.
3. Обучить отборочную модель максимум на 1000 деревьев с `loss_function=RMSE`,
   `learning_rate=0.05`, `depth=6`, `l2_leaf_reg=3`, `random_seed=42`.
   CPU, 4 потока, `has_time=True`; порядок строк сохраняется.
   Если validation RMSE не улучшается 50 итераций, остановиться и выбрать
   лучшее число деревьев. Test в `eval_set` не передаётся.
4. С выбранным числом деревьев заново обучить итоговую модель на всём train.
   Сохранить в родной формат `model.cbm`, загрузить обратно и проверить совпадение
   прогнозов. Test не добавляется в обучение; эта же модель прогнозирует future.
5. Рассчитать на test RMSE/MAE в рублях, MAPE в процентах и R². Для сравнения
   сохранить метрики константного прогноза: средняя цена train для каждого рейса.
   Это диагностический baseline, а не альтернативная обученная модель.
6. Записать прогнозы test/future в Parquet и CSV. Для future поля факта и ошибок
   всегда пустые. Прогнозы не округляются и не обрезаются; число неположительных
   прогнозов сохраняется в отчёте. При неопределённом R² (постоянный target)
   метрика записывается как JSON `null`.

Целевая цена используется в рублях без логарифмирования. Обучаемых скейлеров,
статистической очистки и Optuna здесь нет. Подбор числа деревьев делается только
по внутренней validation; оценка на test не должна использоваться для последующей
настройки параметров этого же эксперимента.

Параметры можно явно передать через `--iterations`, `--depth`, `--learning-rate`,
`--random-seed`, `--thread-count`, `--validation-days`, `--early-stopping-rounds`.

### Артефакты обучения

Каждый запуск создаёт отдельный каталог `ml/artifacts/model-<UUID>/`:

```text
model.cbm                       # модель для повторного predict без fit
metrics.json                    # validation, test, константный baseline
selection_history.csv           # RMSE fit/validation по итерациям
feature_importance.csv          # PredictionValuesChange; не SHAP и не причинный эффект
predictions_test.parquet
predictions_test.csv
predictions_future.parquet
predictions_future.csv
training_report.json            # маркер завершения, параметры, версии и хеши
```

Каждый файл прогнозов содержит ID ставки, дату, города, основной кузов,
категории, `dataset_split`, `actual_price_rub`, `predicted_price_rub`,
`abs_error_rub`, `ape_pct`, название/версию модели, ID запуска и UTC-время скоринга.
Например, факт 100000 и прогноз 95000 дают `abs_error_rub=5000`, `ape_pct=5`.
Для future оба показателя ошибки и факт отсутствуют. CSV записывается в UTF-8 с BOM.

`training_report.json` появляется последним. Без него каталог считается
незавершённым. Параметры, семя, входные файлы и код зафиксированы; `model_version`
строится по обучающим данным и рецепту обучения, без test-цен. ID запуска отличается
при каждом повторе. Бинарные CBM-файлы могут различаться из-за служебного времени;
проверять нужно прогнозы и параметры, а не равенство байтов двух моделей.
Побитовое совпадение между разными ОС/версиями библиотек не гарантируется.

Обучение без публикации можно запустить отдельно в том же образе,
с примонтированным каталогом артефактов:

```powershell
docker compose build ml-features
$datasetName = 'dataset-<UUID>'
docker compose run --rm --no-deps --entrypoint uv ml-features run --no-sync python -m ml.train_model --dataset-dir "/app/ml/artifacts/$datasetName" --output-dir /app/ml/artifacts
```

## Публикация готовых прогнозов в PostgreSQL

DDL находится в `sql/06_mart_ml_price_predictions.sql`. На пустом томе Compose
выполняет его автоматически после справочника `mart.body_groups`. На существующей
БД скрипт нужно применить один раз без удаления тома, например из PowerShell:

```powershell
Get-Content -Raw -Encoding UTF8 sql/06_mart_ml_price_predictions.sql | docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U de_user -d deals_bigdata
```

Пользователя и базу замените на значения вашей конфигурации. Повтор начального DDL
сохраняет данные; `IF NOT EXISTS` не обновляет структуру уже существующей таблицы.

Локально, с настроенными стандартными `PG*` переменными:

```powershell
uv run python -m ml.load_predictions --model-dir 'ml/artifacts/model-<UUID>'
```

В Docker (образ `ml` должен быть собран из актуального кода):

```powershell
$modelName = 'model-<UUID>'
docker compose run --rm --no-deps --entrypoint uv ml run --no-sync python -m ml.load_predictions --model-dir "/app/ml/artifacts/$modelName"
```

Эта команда загружает готовый артефакт, не переобучая модель. Каталог без
`training_report.json`, повреждённые файлы, несовпадающие контекст/ошибки/даты,
нулевые или отрицательные прогнозы отклоняются до публикации. Все восемь файлов,
перечисленных в контракте обучения, должны присутствовать и совпадать по SHA-256.
Future-факт и ошибки должны быть пустыми; загрузчик не исправляет их молча.

### Зерно и поля таблицы

Ключ — `(model_version, as_of_date, source_price_id)`. Одна ставка может иметь
прогнозы разных моделей и разных срезов. Сами `model_run_id` и `dataset_run_id`
описывают происхождение и не входят в бизнес-ключ: новый UUID запуска не создаёт
дубль прогноза. Срез определяет принадлежность к test/future, а не дата загрузки.

- `source_price_id bigint` — логический ID источника, без FK на изменяемый Core.
  Сохранённые исторические прогнозы переживают удаление исходной ставки.
- `loading_date`, коды и названия городов — маршрут на момент скоринга.
  Имена полей `origin_*`/`destination_*` из файлов преобразуются в
  `loading_*`/`unloading_*` для согласованности с Core/Mart.
- `body_group` ссылается на `mart.body_groups`; русское название доступно через JOIN.
  Весовая и объёмная категории сохраняют ограничение Core `varchar(4)`.
- `actual_price_rub`/`predicted_price_rub` — `double precision`, соответствующий
  float64 ML-набора. Значения сохраняются без округления; бухгалтерская точность
  исходных денежных расчётов остаётся в `numeric` Core.
- `abs_error_rub`/`ape_pct` — вычисляемые `GENERATED ALWAYS ... STORED` колонки.
  Ошибки из файлов проверяются, но не копируются: PostgreSQL рассчитывает их сам.
  Пропуск future-факта автоматически даёт NULL в обеих ошибках.
- `model_name`, UUID запуска модели и набора, `scored_at timestamptz`, SHA-256
  отчёта — происхождение результата. `loaded_at timestamptz` — время его записи в БД.

CHECK-ограничения требуют конечных положительных цен/прогнозов и согласованных
дат: test лежит в `[as_of - 21 день, as_of]` с известным фактом; future — строго
после `as_of`, без факта. Прогнозы не обрезаются для прохождения проверок.
Первичный ключ создаёт индекс модели/среза/ID; дополнительный индекс
`(loading_city_gcid, unloading_city_gcid, loading_date)` поддерживает отбор по маршруту.

### Как обеспечивается повторная загрузка

1. Прочитать **оба полных** файла test/future, проверить отчёт, контрольные суммы,
   уникальность ID, даты и соответствие модели. Test обязан быть непустым;
   future может содержать ноль строк. Это не интерфейс загрузки отдельных порций.
2. Взять транзакционную advisory lock публикации. Второй параллельный запуск
   получает ошибку и может быть повторён после первого. Core ETL использует
   отдельный ключ: публикация читает файлы и не зависит от текущих строк Core.
3. Запретить более старый `scored_at` для уже опубликованного `(model_version, as_of)`.
   Два разных артефакта с одинаковым временем также отклоняются. Предполагается,
   что снимки изменяет этот загрузчик; произвольный SQL не обязан соблюдать lock.
4. Через COPY передать строки во временную таблицу с ограничениями целевой схемы.
   Python сериализует строки потока COPY, не выполняя построчные INSERT.
5. Удалить отсутствующие ID только из выбранного снимка. Затем выполнить
   `INSERT ... ON CONFLICT ... DO UPDATE` с `IS DISTINCT FROM`.
6. Проверить итоговые числа строк и закоммитить. При ошибке откатываются и
   удаления, и вставки, и обновления; читатели видят прежний или новый снимок.

Пример: в старом снимке ID `[1, 2, 3]`, в новом `[1, 2]`. ID 3 удаляется,
ID 1 и 2 вставляются/обновляются; другие модели и срезы сохраняются.
Повтор **того же артефакта** не меняет ни одну строку, включая `loaded_at`.
Новый запуск обучения с тем же `model_version` обновляет происхождение и
`loaded_at`, но сохраняет единственность бизнес-ключа. Старый файл после него
будет отклонён — для повтора используйте актуальный опубликованный артефакт.

Загрузчик не вызывает повторный predict и не берёт фактическую цену из текущего
Core: это сохраняет состояние test/future выбранного исторического среза.
JSON-лог успеха содержит `staged`, `inserted_or_updated`, `unchanged`, `deleted`
и числа строк test/future. Операция считается успешной только после коммита.

### Запросы для pgAdmin

```sql
SELECT model_version, as_of_date, dataset_split, count(*) AS rows
FROM mart.ml_price_predictions
GROUP BY model_version, as_of_date, dataset_split
ORDER BY as_of_date DESC, model_version, dataset_split;

SELECT p.source_price_id, p.loading_date,
       p.loading_city_name, p.unloading_city_name, bg.name_ru AS body_group,
       p.actual_price_rub, p.predicted_price_rub, p.abs_error_rub, p.ape_pct
FROM mart.ml_price_predictions p
JOIN mart.body_groups bg USING (body_group)
WHERE p.model_version = '2ff89f0b8b6d7192'
  AND p.as_of_date = DATE '2026-10-26'
ORDER BY p.loading_date, p.source_price_id
LIMIT 100;
```

Версию модели подставьте из отчёта своего запуска. При сравнении метрик и агрегации
выбирайте конкретную модель и срез, чтобы не смешивать несколько прогнозов ставки.

Графики корневого README воспроизводятся командой `python -m ml.plot_report`
по завершённому model-каталогу; изображения и небольшой JSON сохраняются в
`assets/ml`, полный исходный артефакт остаётся в исключённом `ml/artifacts`.

```powershell
uv run python -m tests.run_checks
```

В `tests/test_ml.py` находятся 7 тестов без БД и один интеграционный тест извлечения.
Последний разрешён только с `RUN_ML_INTEGRATION=1` и подключением к **пустой
временной БД** `de_ml_test_*`; runner создаёт её сам. Проверяются дедупликация
городов, несколько кузовов без размножения ставок, фильтры, маскирование будущей
цены и независимость будущих признаков от цены и `outlier_mark`.

Тесты обучения используют маленький набор и настоящий CatBoost: проверяют границу
validation, формулы метрик, загрузку CBM, маскирование future
и независимость обученной модели от изменения цен test. Запись в БД не выполняется.

Три теста `tests/test_predictions.py` проверяют публикацию: повтор без изменений,
вычисляемые ошибки, обновление и удаление исчезнувших ID, пустой future, изоляцию
моделей/срезов и откат после удаления при сбое UPSERT. Они разрешены только при
`RUN_ML_PUBLISH_INTEGRATION=1` и подключении к отдельной БД `de_ml_publish_test_*`;
runner подготавливает её автоматически. Рабочую БД для тестов использовать нельзя.
